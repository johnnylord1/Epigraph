# Technical audit — 2026-09-26

Scope: working tree of branch `codex/theme-system-refactor` after
`feat(first-run): full-window layout, responsive controls, and navigation gating`.
The audit read the repository documentation and the Syncd/Core, desktop
replication, Tauri command, persistence and first-run code paths, then fixed the
defects below with focused regression tests.

This record does not certify a release. The audit environment could not install
npm or crates.io dependencies, so the new tests were first executed in the
follow-up validation pass recorded in [Validation results](#validation-results),
which also found and fixed the defects listed under V-01..V-15.

## Defects fixed

| ID | Area | Problem and impact | Fix |
| --- | --- | --- | --- |
| A-01 | Syncd live stream authorization (`syncd/routes/events.rs`) | `/v1/events` authenticated once when the stream opened. Revoking a device, letting its token expire or removing a scope in *Paired devices* kept delivering changes to an already open stream indefinitely. | The stream re-reads the token state (revocation, inactivity expiry, granted scopes) on every ping and before every change, and closes when the streamed scopes are no longer fully granted. Storage errors also close it. |
| A-02 | Desktop replication resume (`syncd_replication.rs`) | The desktop consumer polled `/v1/changes` and then opened `/v1/events` without `Last-Event-ID`. Changes committed between the poll and the subscription were never delivered; the next live change advanced the checkpoint past them, so they were lost until a full snapshot recovery. | The live stream now resumes with `Last-Event-ID` equal to the polled `currentServerVersion`, so the server replays the gap. |
| A-03 | Suwayomi progress mirror (`syncd/suwayomi_progress_mirror.rs`) | Mirrored `comic.history` and `comic.chapter_state` writes were appended to `change_log` but never broadcast. Live subscribers missed them, and a later broadcast change moved their resume point past the mirrored versions. | Applied mirror writes are broadcast while `mutation_gate` is held, preserving commit order. |
| A-04 | Book library profiles (`lib.rs::write_book_library_state`) | Desktop book replication reads and writes only the **main** book library, but every book-library save from another local profile was diffed and then written back into the main library file (the frontend never sends `bookHistory`, which always triggered the write-back). Using a second local profile overwrote the main profile's books. | Only saves of the main book library notify replication. Other local profiles keep a local-only book library. |
| A-05 | Tauri command boundary (`lib.rs`) | Application commands were registered without an ACL app manifest, so every webview could call them, including the hidden novel runtime host that executes third-party LNReader plugin code with `globalThis`, and the reader/tracker windows that load remote sites. That exposed arbitrary file read/write (`read_file_base64`, `write_file_base64`), profile reset, process and pairing commands to untrusted code, contrary to the runtime-host capability contract. | `main_window_commands_only` rejects application commands from any webview other than `main`. Plugin commands keep their capability permissions; the runtime host already talks to the main window through events only. |
| A-06 | Critical state writes | The desktop Syncd session store (device identity and access tokens), user-selected exports written by `write_file_base64`, the reconciliation overlay and the novel source-classification state were written in place. A crash or full disk mid-write could leave a truncated file; for the session store that silently dropped every pairing. | These writes now use a temporary sibling, `sync_all` and an atomic replace, and remove the temporary file on failure. |
| A-07 | GraphQL client timeout (`src/lib/client.ts`) | `gql` ignored `timeoutMs` whenever the caller supplied an `AbortSignal`. Readiness probes pass both, so a Suwayomi JVM that accepted the connection without answering could stall "wait for Suwayomi" flows indefinitely instead of retrying. | An explicit `timeoutMs` is always honoured and linked to the caller signal. Calls with only a signal keep their previous unbounded behaviour; calls without a signal keep the 12 s default. |
| A-08 | Settings updater progress listener | The `update-progress` listener could be registered after its effect was torn down and then never removed. | The teardown now releases a listener that finishes registering late. |

## New invariants

- A live Syncd stream never outlives the authorization that opened it: revoked,
  expired or narrowed tokens stop receiving data without waiting for a reconnect.
- Every write that appends to `change_log` is broadcast after commit and under
  `mutation_gate`; SSE consumers may therefore deduplicate and resume purely by
  `server_version`.
- A client that switches from `/v1/changes` to `/v1/events` must resume with the
  polled `currentServerVersion` as `Last-Event-ID`.
- Desktop books replication is bound to the main local profile's book library.
- Only the `main` webview may call application commands.
- Files that hold pairing credentials or user exports are replaced atomically.

## Remaining issues

These were confirmed during the audit but not changed, because a safe fix needs a
product or protocol decision. Their status on 2026-09-28 is in
[Remaining issues and open items resolved](#remaining-issues-and-open-items-resolved-2026-09-28).

1. **No durable outbox for a desktop paired with a remote Core.** Desktop edits
   are diffed when the local file is written and submitted once. If the remote
   Core is unreachable, the mutations are dropped; `publish_current_*_state`
   republishes the full local state only when the *local* Core authority is
   activated. Offline edits (including deletes) on a laptop paired with another
   PC therefore never reach the Core. Republishing on every remote reconnect is
   not a safe substitute because desktop mutations carry no event clock and
   would resurrect entities deleted remotely. A persistent, per-profile outbox
   with event clocks is required.
2. **Runtime host can still emit events to the main window.** The novel runtime
   host keeps `core:default`, which lets plugin code emit arbitrary events such
   as `tracker-oauth-callback`. The first-run tracker flow checks a session id;
   the Settings tracker flow does not. Scoping event permissions for the host
   window (or checking the session id in Settings) would close this.
3. **`download_server_file_to_downloads` is registered but unused.** It writes a
   fixed file name into Downloads, contrary to the user-folder rule. It is now
   unreachable from secondary webviews; removing it is left to the owners.
4. **Books for non-main local profiles are local-only.** A-04 prevents data loss
   but does not add per-profile book replication.

## Desktop pairing by PIN

The first-run sync step pairs two computers on the same network. Previously it
needed the QR/link bundle. It now works with a code typed on the new computer.

| Part | Implementation |
| --- | --- |
| PIN | `syncd/pairing_pin.rs`: six digits derived by SHA-256 from the bootstrap session's secret pairing code, so it needs no storage and ends with the session. |
| Route | `POST /v1/pairing/pin/resolve` (`routes/bootstrap.rs`) returns the bootstrap payload of the matching open `bootstrap-*` session. It returns `PAIRING_PIN_NOT_FOUND` for an unknown PIN and `PAIRING_PIN_LOCKED` when locked. |
| Rate limit | 8 failed guesses per 60 s on each host. When a burst reaches the limit, the open bootstrap sessions expire, so the host shows a new PIN. |
| TTL | The bootstrap session default changed from 120 s to 300 s (`syncd/config.rs`). |
| Desktop command | `syncd_resolve_pairing_pin` uses the TLS client pinned to the discovered certificate, tries the advertised origin and then the fallbacks, and returns `SYNC_PIN_*` reason codes. |
| Verification | Both screens show a 4-digit code derived from the host certificate fingerprint (`src/lib/syncPairingVerification.ts`) before the host approves. |
| Host screen | In "Add device", `SyncdConnectionPanel` shows the PIN, a countdown bar and "New code in m:ss". A new session starts automatically when the old one expires. |
| First run | `FirstRunSyncStep.svelte` lists computers found by mDNS and takes the PIN in six slots, with paste supported. It then waits for approval, shows the replicated scopes and finishes when the library is ready. The QR/link flow and manual address remain under "Other ways to connect". |

Tests: `pairing_pin` unit tests, `pairing_pin_resolves_the_open_bootstrap_session_only`
(`syncd/app.rs`), and `FirstRunSyncStep.test.ts` (success, wrong PIN, rejection).

## Detached reader windows (2026-09-27)

The manga, novel and book readers have an **Open in a new window** button in the HUD, next to
the settings button. Several reader windows can be open at once, on different works or the same
chapter, while the main window stays usable.

- **Trust boundary.** Application commands still run only from the `main` webview.
  - A reader window is a `detached-reader-*` webview. Its capability
    (`capabilities/detached-reader.json`) grants window controls and the HTTP plugin only.
  - The few commands a reader needs are relayed by the main window from an allowlist:
    `read_book_library_state`, `read_novel_library_state`, `read_file_base64`,
    `get_cached_library_cover`, `read_extension_compatibility_state`,
    `record_media_audit_event`, `get_suwayomi_update_lock_status`, and the Suwayomi
    operation lease.
  - The lease is accepted only for the `mutation` scope. The main window tracks each
    window's leases and releases them when the window closes, or after 2 minutes: a
    reader's mutation gives up at the 12 s GraphQL timeout, so a lease held that long
    belongs to a window that stopped answering.
  - `is_trusted_command_webview` rejects the reader labels (Rust test).
- **Channel.** Messages travel as Tauri events.
  - Any webview can see these events, including the novel plugin host, so each message is
    sealed with AES-GCM under a per-window key.
  - The key reaches the window in its URL fragment, never through an event. The
    authenticated data binds the direction and window label.
  - Sequence numbers reject replays. Store changes are also limited to an allowlist.
- **Persistence.** The main window remains the only writer.
  - A reader window applies history, bookmarks, settings and book progress locally, then
    hands them to the main window.
  - Manga progress is saved from the reader window through Suwayomi. Its pending journal
    carries the window label, so windows do not overwrite each other. The main window
    adopts a journal left by a window that closed before flushing.
  - Settings and manga bookmarks wait for the main window's answer. Until it arrives, the
    window applies them again on top of any state it adopts from a storage event, so a save
    the main window made just before cannot briefly undo them.
  - Closing a reader window flushes progress and waits for the main window's answers
    before the window is destroyed.
- **Novels.** The novel runtime host runs only in the main window, and only the main window
  writes the novel library.
  - A novel window asks the main window for each chapter (`loadNovelChapter`), which reads
    the offline cache or the source and caches it as before.
  - Progress and bookmarks go over as operations (`saveNovelReaderChanges`), not as a
    library snapshot. The main window applies them to the library it has at that moment, so
    a window cannot undo edits made meanwhile in the main window or in another window. A
    bookmark operation carries the state to set, so applying it twice changes nothing.
    After saving them, the main window tells an open novel page, which shows the new
    progress and bookmarks without being reopened.
  - The window keeps its own copy of the library for the next chapter; it never calls
    `write_novel_library_state`.
  - Closing the window from its title bar goes through the reader's exit, so progress is
    saved first. Discord presence stays with the main window.
- **Downloaded manga chapters.** A reader window does not receive the archive. The main
  window unpacks it and hands the pages over one per message (`openOfflineMangaChapter`,
  `readOfflineMangaPage`), forgetting each page once taken; pages a closed window never took
  expire after 2 minutes.
- **Page list handover.** The main window passes the chapter's page URLs it already fetched.
  - Found in the E2E run: detaching while the main window was still loading a chapter's
    pages made the new window's `fetchChapterPages` wait on Suwayomi (7.7 s for 21 pages,
    over the 12 s GraphQL timeout for 53 pages), and the chapter failed to load.
  - A plain `{ __typename }` query answered in 37 ms at the same moment, so the wait is
    Suwayomi holding a second page-list request for a chapter it is still downloading.
  - The new window takes the list only if every entry is an http(s) URL
    (`readDetachedPageUrls`). Offline blob URLs are never handed over.
  - Any other chapter a reader window opens gets its list from the main window
    (`fetchChapterPages`). Page-list requests for the same chapter that overlap share one
    Suwayomi request (`fetchSourceChapterPages`), so two windows, or the docked reader and
    a window, opening the same not-yet-cached chapter no longer queue a second request
    behind the first.
- **Relay loop (found in the E2E run).** An idle reader window sent `addHistory` and
  `addBookmark` to the main window about every 8 ms, without end.
  - Each save in the main window fires a storage event. The reader window then replaced
    `store.settings`, and the reader's history effect tracked `store.settings.autoBookmark`,
    so it ran again and relayed both calls back.
  - The main window handles a window's messages in order, so lease requests, saves and the
    close queued behind the flood. Closing from the HUD took about 18 s on a blank window,
    and a chapter the window opened could look stuck.
  - The effect now reads `autoBookmark` untracked. An idle window now sends nothing, and
    closing takes about 150 ms with progress saved.
- **Keyboard (found in the E2E run, not specific to reader windows).** Clicking the page
  focuses the viewer inside the HUD's tap target, which has `role="button"`.
  `isReaderControlKeyboardTarget` treated every key as aimed at a control, so paging keys,
  `f` and the chapter keys did nothing after a click, in the main window too. The tap target
  is now marked `data-reader-surface` and exempted.
- **EPUB resume (found in the E2E run, not specific to reader windows).** Every reopen of
  an EPUB went back one page (20.6 % to 17.6 % to 14.7 %), and moving the book to a window is
  a reopen too.
  - epub.js chose the page for the saved CFI before the reader's own stylesheet was
    injected. The reflow pushed the saved word onto the next page while the view stayed on
    the previous one, and `relocated` then saved the start of that earlier page.
  - After the stylesheet is in place and fonts are ready, `loadEpub` shows the saved spot
    again. Mid-paragraph and chapter-start positions now hold through two docked reopens
    and a detach.
- **Behaviour.**
  - The reader window uses the same theme, zoom and language as the main window. It has its
    own fullscreen, and Escape leaves it.
  - Closing the main window closes the app and every reader window.
  - Discord presence stays with the main window. The source web view and "open in
    browser" actions are hidden in reader windows.

## Remaining issues and open items resolved (2026-09-28)

### Remaining issues

1. **Durable outbox. Resolved.**
   - Desktop mutations that could not be delivered are kept per local profile in
     `syncd-outbox.json`, in the desktop state directory, written atomically.
     - The file records the endpoint the mutations were addressed to: the local
       authority or a paired session.
     - An unreadable file is set aside as `syncd-outbox.json.corrupt-<ms>`
       instead of blocking sync.
   - Every submit sends the queued mutations first, then the new ones, in order, in
     chunks of 250.
     - An unreachable Core or an expired session stops the delivery, and the
       unsent rest stays queued in order.
     - A chunk the Core rejects is reported and not retried, because resending the
       same content would fail again. It does not hold back later chunks.
   - The queue is also flushed when replication reaches the live state, for the
     local authority and for a paired Core.
   - Each queued mutation keeps its original `clientMutationId` and lamport clock,
     byte for byte.
     - The Core recognizes a resent mutation by device and `clientMutationId` and
       returns the stored receipt, so a batch interrupted after the Core applied it
       is not applied twice.
     - Because the clock is the original one, an offline edit cannot resurrect an
       entity deleted later on another device. That is why a full republish on
       reconnect was not a safe substitute.
   - Queue maintenance:
     - A mutation already queued is not queued twice.
     - A delete drops older queued writes to the same entity.
     - The queue holds at most 20,000 mutations per profile; beyond that the oldest
       are dropped and logged.
     - A queue addressed to an endpoint that is no longer the active one is dropped
       and logged. The new endpoint receives the current library state when it
       bootstraps.
     - A queued novel plugin change whose plugin files changed meanwhile is dropped,
       because the plugin's current state is published on its own.
   - **Found while testing it: every offline error was classified as degraded.**
     - `reqwest` prints only "error sending request for url (...)"; the cause
       ("tcp connect error", "connection refused", "timed out") is in the error's
       source chain.
     - So a stopped Core was reported as *Degraded* instead of *Offline*, and the
       fallback origins of a paired session were never tried after a refused
       connection.
     - `transport_error_message` now includes the source chain at every Syncd
       request.
   - Tests in `syncd_replication.rs`:
     - `outbound_mutations_survive_a_serde_roundtrip_unchanged`
     - `outbound_queue_dedupes_compacts_deletes_and_stays_bounded`
     - `outbound_queue_persists_per_profile_and_quarantines_unreadable_files`
     - `mutation_delivery_is_chunked_and_a_rejected_chunk_does_not_block_the_rest`
     - `mutation_delivery_stops_at_an_expired_session_and_keeps_the_rest_in_order`
     - `mutation_delivery_to_a_stopped_core_is_retryable_and_classified_offline`
       (a real closed port; it failed before the source-chain fix).
2. **Tracker login event. Resolved.** The Settings tracker login now creates a session
   id, passes it to `open_tracker_oauth_window`, and ignores a
   `tracker-oauth-callback` event without that id, as first run already did. Another
   webview emitting the event can no longer complete or hijack a login (test in
   `Settings.test.ts`).
3. **`download_server_file_to_downloads`. Resolved.** The unused command was removed,
   with its registration.
4. **Books for non-main local profiles. Kept by design, documented.**
   - The Core has a single books scope, `books:global`. The pairing scopes are
     `books:global`, `novels:profile:{id}` and `comics:profile:{id}`.
   - The main local profile's book library is the one bound to `books:global`. Other
     local profiles keep a local-only book library, which A-04 protects from being
     written into the main one.
   - Replicating books per profile would need a new Core scope
     (`books:profile:{id}`), schema and snapshot changes, and new pairing scopes on
     every paired client. That is a protocol change, not a fix.

### Still open items

1. **Long paths. Resolved.**
   - Every atomic replace now goes through
     `suwayomi_maintenance::atomic_replace_file`, which uses the verbatim prefix
     beyond `MAX_PATH`: `tls.rs`, `syncd/runtime_manifest.rs`,
     `syncd/suwayomi_process.rs` and `syncd_replication.rs`.
   - `MoveFileExW` remains only in that function.
2. **Flaky tests. Causes fixed.**
   - `mutations::concurrent_identical_retries_apply_once`: a transaction that reads
     first and writes later cannot upgrade its lock once another connection has
     committed. SQLite fails it at once with "database is locked", without waiting
     for `busy_timeout`. That was a real Core defect under concurrent writes, not
     only in the test. Write transactions now start with `BEGIN IMMEDIATE`
     (`db::begin_write`) and wait for the lock.
   - `portable_manifest::expired_snapshot_is_removed_and_rejected`: tests running in
     parallel shared the global snapshot cache and evicted each other's entries. The
     tests that use the cache now take turns (`snapshot_cache_turn`).
   - The Vitest timeouts under full-suite load are recorded in
     [Validation (2026-09-28)](#validation-2026-09-28).
3. **`svelte-check`. Resolved:** 0 errors.
   - The 54 remaining warnings are unused CSS selectors in
     `SyncdConnectionPanel.svelte`. They were already there and are kept on purpose:
     the theme token-consumption test and the theme probe read those rules.
4. **English-only diagnostics. Resolved where a user can see them.**
   - The media audit toasts (books and novels restore loaded or classified, manga
     restored) are localized.
   - The restore-plan summary is now built from counts (`restorePlanSummary`)
     instead of the planner's English `summaryLabel`.
   - The extension compatibility stage labels in the extension settings panel are
     localized.
   - Extension health reasons (`manga/runtime/health.ts`) and the restore planner's
     per-entry prose stay English. They are internal diagnostics written to logs and
     support exports; the UI shows the localized reason code instead.
5. **Genre tags. By design.** Genre tags and other metadata provided by a source stay
   in the source's language. They are also the values sent back to the source as
   filters, so translating them would break filtering.
6. **Book import. Resolved.** The books library toolbar has an import button that
   opens a file picker for EPUB and PDF; drag and drop still works.
7. **"Main profile" wording. Resolved.** The built-in profiles are shown as
   Default and Test, a profile without a name as Custom, and a profile chosen for
   one launch says so.
8. **Translations. Partly resolved.**
   - The profile vocabulary was unified in Japanese (プロファイル) and Simplified
     Chinese (配置文件). Chinese used 型材, which means a metal profile.
   - A native speaker's review of pt-BR, es, ja and zh-CN is still advisable. It
     cannot be done by the audit.
9. **Detached reader windows. Limits kept by design:**
   - Settings changed in one reader window reach the others through the main window.
     - The window applies the change at once and sends it to the main window.
     - The main window saves it, and every other window adopts it from the storage
       event.
     - A change the main window refuses is dropped the next time the window adopts
       the saved state.
   - Two windows reading the same novel save progress last-writer-wins, as two
     devices do.
   - Each novel window reads the whole novel library once through the channel when
     it opens.
   - Starting FlareSolverr from a novel window is not available; the main window
     does it.
   - A page list requested after an earlier one finished is not shared, so a chapter
     that Suwayomi is still downloading can wait as it does in a single window.
   - Monitors. A new reader window used to open centred on the primary monitor even
     when the main window was on another one. It now opens centred in the work area
     of the monitor that shows the main window, at the default size scaled to that
     monitor and kept inside it (`detachedWindowPlacement`, tested). It is created
     hidden and shown once placed, so it does not appear on the wrong monitor first.
     Each window then keeps its own size and position, and its content follows its
     own monitor's scale. There is no per-window zoom, and a window's position is not
     remembered after it closes.
10. **Manga progress while offline. Verified, no change needed.**
    - A page change that cannot reach Suwayomi stays in the pending journal in
      `localStorage`, keyed by scope and reader window.
    - The journal is sent again on the next page change, when a reader opens, on the
      browser `online` event, when the page is hidden or unloaded, when Settings
      closes, when a reader window closes, and after a restart. It is cleared only
      after Suwayomi accepts it
      (`mangaProgress.test.ts`, `mangaProgressRuntime.test.ts`).
    - There is no timer retry: if nothing above happens, the update waits in the
      journal. It is not lost.
